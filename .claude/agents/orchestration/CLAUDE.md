# Orchestration Rules

複数ファイルにまたがる実装タスクでは、あなた(メインセッション)はオーケストレーターとして振る舞う。自分で実装せず、判断・分解・統合に専念する。

エージェント定義はユーザーレベル(`~/.claude/agents/orchestration/`)にあり、どのプロジェクトでも利用できる。

## 適用条件

- **適用する**: 複数ファイルにまたがる実装、機能追加、リファクタリング
- **適用しない**: 質問応答、1〜2行の軽微な修正、設定変更、ドキュメントのみの変更(これらは直接対応してよい)

## 役割分担(厳守)

- 要件定義・設計・タスク分解・統合・完了判定: メインセッション(あなた)
- コードベース探索・調査: explore agent (haiku)
- 実装・テスト作成: impl-worker agent (sonnet)
- 高難度実装(並行処理/複雑なアルゴリズム/レガシー絡み): hard-impl agent (opus)
- コードレビュー・セキュリティ監査: reviewer agent (opus)

## ワークフロー(5フェーズ)

1. **Explore**: 実装前に必ずexplore agentで調査する。自分でGrep/Globを多用しない。
   探索結果は「要約のみ」を受け取り、ファイル全文をメインコンテキストに持ち込まない。
2. **Plan**: 調査結果からタスクを実装単位に分解し、各タスクにspecを書く。
   specには必ず含める: 対象ファイル、変更内容、受け入れ条件、やらないこと(スコープ外)。
   タスク間の依存関係を明示し、独立と確認できたタスクのみ並列化する。依存があれば直列。
3. **Build**: 各specをimpl-workerにディスパッチする。1タスク=1エージェント。
   以下のいずれかに該当する場合のみhard-implへエスカレーション:
   並行処理・分散一貫性 / 計算量が支配的なアルゴリズム / 既存挙動を壊せないレガシー修正。
4. **Verify**: 実装完了後、reviewer agentにレビューさせる(実装エージェントに自己レビューさせない)。
   指摘はspecに反映し、修正はimpl-workerに再ディスパッチ。テスト実行はimpl-workerが行う。
5. **Integrate**: 全成果物を統合し、spec受け入れ条件との照合・矛盾検出を行う。
   全条件を満たすまで完了と宣言しない。満たせない場合は理由と残作業を報告する。

## 禁止事項

- specなしでの実装ディスパッチ
- 依存関係未確認での並列実行
- レビュー未実施でのマージ・完了宣言
- スコープ外機能の追加(specの「やらないこと」を実装したら差し戻す)
